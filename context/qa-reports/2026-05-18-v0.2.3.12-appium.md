## 1. Method comparison: why Appium pass after CDP pass

The first QA used Chrome DevTools Protocol (CDP) `Runtime.evaluate` to click buttons via JS — which bypasses React-Aria / Capacitor touch chains. Some bugs that depend on real touch events (e.g. native pointer DOM/onTouchStart vs synthetic JS click) didn't reproduce under CDP.

This Appium pass uses W3C pointer actions (`performActions` with `pointerType: 'touch'`) which deliver real Android `MotionEvent ACTION_DOWN/UP` through UiAutomator2, the same event chain a human finger produces.

## 3. NB-4 detailed evidence (this round)

**Setup:**
- Created test dose via SQL: `INSERT INTO medcontrol.doses ... medName='NB4 Appium Test' status='pending' scheduledAt=NOW()-5min` → id `0821fca5-261c-44ed-91b4-bc8254f5b9ca`

**Execution:**
1. Appium tap dose card at (540, 1630) → DoseModal opened. UI dump confirmed Tomada button at `[714,2142][1026,2271]` (center 870, 2206).
2. Appium W3C real touch on Tomada button — `pointerType: 'touch'` with `ACTION_DOWN`/`ACTION_UP` at native MotionEvent level. T0=tap initiated.
3. **In the SAME Node.js process**, called `adb shell am force-stop com.dosyapp.dosy.dev` synchronously after the tap returned.
4. Delta: tap done at T1, force-stop sent at T2. **T2 - T1 = 217ms.**
5. App re-launched. UI rendered: counter `0/1` (1 pendente), dose still labeled "atrasada", no "tomada" badge.
6. DB verified: `status='pending'`, `actualTime=null`, `updatedAt=2026-05-18 15:06:38` (insert time, never updated).

**Comparison with sanity test (same flow no force-stop):**
- Adesão went 33%→67%, atrasadas 2→1. The mark **does propagate to DB** in normal flow within 1-2s.
- With force-stop @217ms: mark is irreversibly lost.

**Conclusion:** NB-4 is reproducible with real Android touch events, not a CDP artifact. The bug is in the mutation persistence path — `confirmDose` `onMutate` does not flush mutation queue to IndexedDB synchronously before returning. If the OS kills the process before TanStack's throttled async serialization (now 5000ms after v0.2.3.7 #275 — see `main.jsx:155`) writes the mutation to IDB, the optimistic UI patch is lost and the network call never lands.

**Critical context:** v0.2.3.7 #275 increased `throttleTime` from 1000ms→5000ms specifically to reduce IDB pressure. This makes NB-4's reproduction window 5x larger than before. The commit note (`main.jsx:142-145`) acknowledges "Crash-safety preservado pela fila offline de mutations (#204 v0.2.1.7) com shouldDehydrateMutation: () => true". This claim is **invalidated by NB-4 evidence**: a kill within the throttle window still loses the mark.

**Recommended fix priority (per first report):**
1. Add immediate persistence (`persister.persistClient()` call) inside `confirmDose` onMutate, OR
2. Reduce throttleTime back to 1000ms OR add an explicit `persistImmediately: true` option for safety-critical mutations.
3. Add `_optimistic: true` flag to dose patches in `mutationRegistry.js:158-198` (Bug #2) so UI can show sync-pending indicator.

## 4. Bug #10 partial test (this round)

**Setup:**
- `UPDATE auth.refresh_tokens SET revoked=true WHERE user_id::uuid=<teste-plus> AND revoked=false` → 3 tokens revoked (ids 1539, 1541, 1550).
- `adb shell input keyevent KEYCODE_HOME` at T=1779117172.
- App backgrounded 4 minutes (below SOFT_RECOVER_THRESHOLD_MS=5min).

**Result:**
- App resumed cleanly; no "long idle" log line in `useAppResume.js:61`.
- Inactivity calc shows < 5min so short-idle path taken (no refresh attempt by hook).
- Direct CDP-fetch test to `/auth/v1/token?grant_type=refresh_token` with revoked token returned 400 `refresh_token_already_used` in 832ms.
- Error message would match `/invalid.*refresh/i` regex in `useAppResume.js:85-88` → `isAuthFailure=true` → `signOut via listener`. Path looks correct.

**Conclusion:** Bug #10 NOT reproduced in this short-idle test. The >5min idle path with broken refresh chain would need a full 5+ minute background wait, which was attempted but cancelled to preserve time budget. Code path appears robust per review.

## 5. Other bugs status (no live re-test, code-confirmed only)

### Bug #4 useUpdateUserPrefs slow network — REAL, code-confirmed
- `src/hooks/useUserPrefs.js:91-132` `useUpdateUserPrefs` mutationFn calls `supabase.upsert()` at line 110-117 WITHOUT `Promise.race` timeout wrapper.
- Compared to `usePullToRefresh.js:65-87` which uses `Promise.race([fn, 20s reject])` (the v0.2.3.12 fix for PTR).
- If network is slow (cellular 30s+ latency), the mutation hangs:
  - Optimistic UI flip already done at line 98-99 (`writeLocal` + `setQueryData`)
  - `syncUserPrefs` native call (line 121-127) only fires AFTER upsert resolves → native config drifts from web cache.
  - No spinner; no revert on hang.
- Real-world impact: user toggles DnD, sees it flip ON, but criticalAlarm scheduling on the native side keeps DnD as OFF until network finally responds (or never).

### Bug #5 unshare no timeout — REAL, code-confirmed
- `src/services/sharesService.js:51-58` `unsharePatient` is bare `supabase.rpc('unshare_patient')` with no Promise.race.
- Asymmetric with `sharePatientByEmail` (line 32-49) which got the 15s timeout in v0.2.3.7 Bug C fix.
- On slow network, unshare button shows no progress, no revert, hangs indefinitely on the loading spinner of the SharePatientSheet.

### Bug #7 togglePush FCM fail revert — REAL, code-confirmed
- `Settings/index.jsx:89-111` `togglePush` awaits `subscribe(notif.advanceMins)`.
- `subscribe` calls `subscribeFcm` in `fcm.js:25-48` which awaits `PushNotifications.register()`.
- BUT: `register()` resolves before FCM actually returns a token. The token (or failure) arrives later via `PushNotifications.addListener('registration' | 'registrationError', ...)` in `bindFcmListenersOnce` (`fcm.js:138-170`).
- `registrationError` (line 168-170) only `console.error`s — no toast, no state revert.
- Visible impact: user taps push toggle on a device without Google Play Services → toast "ativadas" + toggle ON in UI + `notif.push=true` in local cache, but no actual FCM token = no push will arrive forever.

### Bug #8 TreatmentForm template — code looks safe
- `TreatmentForm.jsx:215-220` template creation is sequential after `create.mutateAsync`, error path catches at line 225-227.

### Bug #9 Multi-dose batch desync — DEFERRED
- Live rapid-tap test not executed. First QA (sequential manual marks) did not reproduce.

### NB-1 useTreatments cache stale — REAL, code unchanged
- `src/hooks/useTreatments.js:14-15` still has `staleTime: 30*60_000` + `refetchOnMount: false`.

## 7. Methodology notes for future QA

### What Appium added vs CDP

1. **Real touch event chain**: NB-4 reproduced identically with W3C pointer actions through UiAutomator2 — confirms it's not a CDP timing artifact.
2. **DoseModal opens via real tap**: confirms React-Native dose card's `onClick` is reachable by native touch (was reachable by CDP too in this case, but in general react-aria/Headless components require real touch).
3. **Inability to validate Bug #8 PatientPicker** remains — would require live touch through Settings → New Treatment → Picker dropdown, which time didn't allow.

### What CDP fetch-patch added

- Used `window.fetch` monkey-patching to inject 30s delay on `/user_prefs` POST to simulate slow network for Bug #4. Patch installed successfully (verified via return value); UI flow to reach DnD toggle was blocked by Push being OFF (nesting). For future runs: enable Push first via toggle (will fail to bind FCM in emulator but local pref update happens), then toggle DnD with patched fetch.

### Egress observations from this run

- During 30min QA session: minimal Supabase REST calls beyond the typical dose query cycle. No request storms after force-stop+resume.
- Logcat shows `secureStorage internalGetItem auth-token` polling pattern after resume (~2x per minute) — TanStack focusManager + Capacitor appStateChange both trigger token fetch. Already mitigated by debounce (`useAppResume.js:38-39`, RESUME_DEBOUNCE_MS=1000).
