## 2. Per-test outcomes

### Test 1 — NB-4 throttle 1s — Mark persists on rapid kill

**Fix:** `src/main.jsx:155-160,164` — throttleTime 5000ms → 1000ms (5× faster IDB flush).

**Method:**
- Created dose `V12 Test Mark` via SQL (scheduled NOW-5min, status pending).
- Appium W3C real touch tap on dose card → DoseModal opens.
- Appium W3C real touch on `Tomada` button (center 870, 2206).
- `adb shell am force-stop com.dosyapp.dosy.dev` triggered at controllable delay after tap.
- App re-launched, DB state polled.

**Two scenarios run:**

| Kill delay | Dose | Final DB state | Outcome |
|---|---|---|---|
| **0ms (immediate, ~243ms after Appium tap return)** | V12 Mark Fast | `status='pending'`, `actualTime=NULL`, updatedAt=insert time | DATA LOST |
| **1500ms (CRITICAL_DELTA=1642ms)** | V12 Test Mark | `status='done'`, `actualTime='2026-05-18 15:47:27.898'`, updatedAt=15:47:29.981 | PERSISTED |

**Logcat evidence:** Force-stop captured at `T+1642ms` in Test 1b, network mutation completed before kill — both IDB write AND network propagation succeeded.

**Status: ✅ PASS for fix's intended scope, but ⚠️ partial coverage**

The fix narrows the data-loss window from 5000ms → 1000ms (5× reduction) as designed. **However, a kill within 1000ms of tap still loses data** — the throttle window is necessarily non-zero unless every mutation triggers immediate sync persist (which the fix does NOT do). This is a known trade-off documented in `main.jsx:141-149`. The fix's narrative says "1000ms < 5000ms = better", but a real user closing the app within 1s still loses the mark.

**Recommendation:** For full crash-safety, a follow-up fix should add `persister.persistClient()` flush inside `confirmDose` onMutate, or set `throttleTime: 0` for mutation queue persistence (separate from cache).

### Test 4 — Bug #7 subscribeFcm await registration

**Fix:** `src/services/notifications/fcm.js:43-73` — `await Promise.race([registrationPromise, 10s timeout reject])` AFTER `PushNotifications.register()` resolves.

**Method attempted:**
- Method A: `pm disable-user com.google.android.gms` → app crashed (GMS is a Capacitor dependency). Re-enabled GMS, restarted app, re-logged in.
- Method B: Patched `Capacitor.toNative` to block PushNotifications.register() callback. The patch successfully intercepted register calls but didn't fully resolve the async chain (register hung instead of resolving + timeout firing).
- Method B-bis: Patched `Capacitor.Plugins.PushNotifications.addListener` to suppress registration events. The push toggle click via Appium W3C real touch didn't reach togglePush handler in logcat (no `PushNotifications.checkPermissions` log line after tap).

**Live reproduction status:** Could not consistently trigger the 10s timeout path within time budget. The Capacitor plugin abstraction makes this hard to mock at JS level without a real GMS-less environment.

**Code review confirmation:**
The fix at `fcm.js:43-73` is correctly structured:
1. Permission check + permission grant verification.
2. addListener('registration') → `resolve()` on success.
3. addListener('registrationError') → `reject(new Error('FCM_REGISTRATION_FAILED'))`.
4. `await PushNotifications.register()` (call native).
5. `await Promise.race([registrationPromise, setTimeout 10s reject 'FCM_REGISTRATION_TIMEOUT'])`.
6. Cleanup in `finally` block.

The previous QA (`qa_report_v0_2_3_12_appium.md` line 31) code-confirmed Bug #7 as REAL. The current implementation correctly addresses the silent-broken-state path.

**Status: ⚠️ PARTIAL** — Fix is code-confirmed correct, but live reproduction in current emulator environment was not achieved within budget. Recommend manual smoke test on a device with intentionally broken FCM (e.g. China ROM without Play Services) before broad ship.

## 4. New issues discovered during validation

### Issue A (minor): JWT expiration mid-session → shares query 401
Mid-test the JWT expired (60min lifetime), causing `list_patient_shares` RPC to return 401. The app's "Carregando…" state persisted indefinitely instead of triggering a session refresh or auth-failure toast.

**Severity:** Low (mostly affects long-running test sessions; production users hit refresh-token flow before expiry). But the silent "Carregando" suggests `useShares.js` doesn't display query errors — see `usePatientShares` has no `onError` handler. Worth a follow-up small fix to display "Erro ao carregar compartilhamentos" toast or inline message on query.error.

### Issue B (CLAIM REVIEW): NB-4 narrative claims "data loss eliminated"
The commit message reads "zero data loss em force-kill" but technically a kill within 1000ms still loses data (verified at 243ms). The fix narrows but doesn't eliminate the window. Code comment at `main.jsx:147-149` says "zero data loss" which is misleading.

**Recommendation:** Update comment to "≤80% reduction in data loss window" or add a true sync-persist call inside critical mutations like confirmDose. Healthcare context warrants both narratives + actual fix.
