## 3. NB-4 flushPersistImmediate validation (Priority 1)

**Metodologia:**
- 3 doses test inseridas via Supabase MCP linkadas a treatment "NB4 Final Test" (Paciente Share LH, teste-plus user), `scheduledAt = NOW() - 6/7/8 min` (aparecem em "Atrasadas").
- Appium W3C tap dose card → modal Tomada → tap "Tomada" botão → `adb shell am force-stop` após delay configurável.
- Após reopen, verificar `medcontrol.doses.status` via Supabase MCP.

**Resultados:**

| Test | Delay configurado | Elapsed real (RPC overhead) | DB status pós-reopen | Veredicto |
|---|---|---|---|---|
| A | 100ms | 114ms | `pending` (mutation NÃO persistida) | **FAIL** |
| D | 200ms | 204ms | `pending` (mutation NÃO persistida) | **FAIL** |
| B | 300ms | 305ms | `done` + `actualTime=17:48:42.449+00` | **PASS** |
| C | 600ms | 612ms | `done` (Test B drain já tinha persistido o item) | **PASS** |

**Conclusão NB-4:**
- Threshold real para `flushPersistImmediate` persistir mutation crítica: **~250-300ms** (não ~100ms como o comment do fix afirma).
- Comment em `mutationRegistry.js:55-59` super-otimista. IDB async write + dehydrate + persistClient leva ~250-300ms no emulator x86_64 API 35 — provavelmente similar ou pior em ARM real low-end.
- **Janela de risco residual:** force-kill em ≤200ms continua perdendo dose silenciosamente.
- **Comparado à baseline anterior (throttle 1000ms):** redução ~3-4× da janela de loss (1000ms → ~250ms). Significativo mas não 10× como o commit message sugere.

**Recomendação:** documentar threshold real no comment + abrir item P3 "investigar persistClient síncrono fallback ou retry imediato pós-mount" futuramente.
