## Origem

User-reportado: cuidador offline no horário do fire, alarme local pré-agendado disparou mesmo após outro cuidador marcar dose como tomada. Risco de dose duplicada.

User-frase:
> "minha esposa estava dormindo... dei era 15:30 e marquei como tomada... celular dela despertou da mesma forma 16h, poderia ter dado a dose duplicada, isso é critico"

Diretiva: "faça a primeira etapa pra mitigar um pouco esses bugs... alarm precisa identificar se esta online ou não, ou se Banco não respondeu por algum motivo... se esse for o caso, precisa ter um DISCLAIMER bem destacado no alarme... Essa mensagem aparece apenas se esse tratamento é de um paciente compartilhado... Alarmes padrão, que são de pacientes sem share, permanecem como estão agora pra não regredir"

## Análise prévia (Plano A vs B)

- **Plano A (mitigação)**: pre-check HTTP no AlarmReceiver + disclaimer visual
- **Plano A++**: cron retroativo cancel pós-update status

User aprovou Plano A primeira etapa. Plano A++ e B parqueados.

## Fluxo pre-check (paciente compartilhado)

```
AlarmReceiver.onReceive
  ↓
collectSharedDoseIds (read isShared per dose)
  ↓ vazio (não shared)
dispatchAlarm direto → fluxo original (zero regressão)
  ↓ algum shared
goAsync + worker thread:
  ↓
runPreCheck:
  ├ online + HTTP success:
  │   ├ todas done/cancelled/skipped → cancela alarme
  │   ├ alguma pending → fire SEM disclaimer
  │   └ atualiza cache
  └ HTTP fail (offline/timeout):
      ├ cache: todas resolved → cancela alarme
      └ cache: alguma unknown → fire COM disclaimer (unverifiedShared=true)
  ↓
dispatchAlarm(unverifiedShared) → AlarmService → AlarmActivity
```

## Decisões arquiteturais

### Pre-check via goAsync + worker thread

BroadcastReceiver onReceive limite 10s. HTTP timeout 1.5s + cache lookup ~10ms = headroom amplo. Worker thread evita bloquear main thread. Fail-safe: catch genérico assume offline → dispara COM disclaimer (erro pelo lado seguro).

### Cache via SharedPrefs MODE_PRIVATE

Trade-off: in-memory caching de SharedPreferences impede ver mudanças externas até reload processo. Aceito porque cache só é populado via FCM cancel_alarms que sempre vem do mesmo processo. Reload externo é raro (BootReceiver após reboot).

### isShared=false default em Worker + JS

Worker fallback 6h não enrich patient_shares (TODO próxima iteração). JS unifiedScheduler aceita campo mas nenhum caller seta hoje. Gap aceito: FCM Edge é o path primário; Worker e JS-foreground cobrem casos raros sem pre-check.
