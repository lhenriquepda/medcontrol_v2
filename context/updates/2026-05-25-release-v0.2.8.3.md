## Bug #0031 (P1 crônico) — FIXED

**Sintoma user (relatado 2026-05-25 21:25 BRT, mesma classe v0.2.6.6 #0023):**
> "às vezes ao iniciar app com boot, fica carregando fila de envio de modificações, mesmo estando com internet... mods estavam indo pra fila SEMPRE depois de um force-kill do app... ou idle longo... e ficava la, app aberto, internet OK, e mesmo assim mods ficavam presas na fila... não quero ter que reiniciar app pra drenar"

**Root cause analysis profundo (5 problemas combinados):**

1. **Drain SERIAL FIFO** — backlog de N entries × 30s timeout cold-start = 30·N segundos UI stuck banner. 5 doses = 150s.
2. **Terser strippava `console.warn`** em prod desde v0.2.7.0 — diagnose impossível em logcat, ficava adivinhando root cause.
3. **TanStack `onlineManager.subscribe` ignorado** — markDose só ouvia `window 'online'` event que em Capacitor Android dispara prematuramente (logcat 2026-05-10 09:24:38: 7ms antes Capacitor confirmar).
4. **Boot drain fire-and-forget 1×** — se primeira tentativa falhava silenciosamente (processLock zombie, fetch hang antes do timeout), não havia 2ª chance até watchdog 30s.
5. **Watchdog 30s lento** demais pra healthcare critical.

## 5 Fixes aplicados (BUG #0031)

### F1 — Drain PARALELO por doseId
**Arquivo:** `src/services/markDose.js`
`_runDrain` reescrito: agrupa entries por `doseId` via Map (mesma dose mantém ordem FIFO; doses diferentes correm via `Promise.allSettled`). Backlog de N doses únicas drena em ~3s, não 30·N. Idempotência via `mutation_log` PK `request_id` garante safety.

### F2 — onlineManager.subscribe + window 'online' dual
**Arquivo:** `src/services/markDose.js`
```js
window.addEventListener('online', () => triggerDrain('window.online'))
import('@tanstack/react-query').then(({ onlineManager }) => {
  onlineManager.subscribe((isOnline) => {
    if (isOnline) triggerDrain('tanstack.onlineManager')
  })
})
```
TanStack onlineManager é fonte mais confiável em Capacitor Android (atualizada via Capacitor.Network bridge em main.jsx). Dual subscriber garante que pelo menos UMA delas dispare drain pós-reconnect.

### F3 — Boot drain DUAS rodadas
**Arquivo:** `src/main.jsx`
```js
drainPendingMutations({ rpcTimeoutMs: 30_000 }).catch(...)  // 1ª @ +0s, cold start budget
setTimeout(() => {
  drainPendingMutations({ rpcTimeoutMs: 15_000 }).catch(...)  // 2ª @ +15s, captures falha silenciosa
}, 15_000)
```

### F4 — Watchdog 30s → 10s
**Arquivo:** `src/services/markDose.js`
Em healthcare critical, 30s de dose stuck é eternidade. 10s = compromise entre snappy recovery e custo idle (1 queueSize check a cada 10s é trivial).

### F5 — Terser preserve console.warn
**Arquivo:** `vite.config.js`
Removido `console.warn` de `terserOptions.compress.pure_funcs`. Logs `[drain] start — queue size: N`, `[drain] grouped into M unique doseIds`, `[drain] done — drained: X transient: Y real: Z`, `[drain] trigger via tanstack.onlineManager` agora visíveis em prod logcat. Trade-off: log size +~2KB gzipped, debug crítico viável.

## Bug #0025 (P1) — FIXED

**Root cause REAL identificado durante QA:**
`mutations.networkMode: 'offlineFirst'` default em main.jsx faz TanStack PAUSAR mutation quando `onlineManager.isOnline()=false` (race durante boot/resume). mutationFn nunca executa → btn "Cadastrar paciente" stuck disabled, zero requests pra Supabase.

**Fix:** `networkMode: 'always'` em mutationRegistry pra createPatient/updatePatient/deletePatient/createTreatment/updateTreatment/deleteTreatment/pauseTreatment/resumeTreatment/endTreatment. Doses mutations (confirmDose/skipDose/undoDose) **mantidas em offlineFirst** porque elas usam pendingMutationsQueue drain pattern (queue-aware).

Validado QA round 3 (2026-05-25 21:05 BRT): criar paciente em **2s** (era stuck 30s+).

## Bug #0026 (P2) — FIXED

**Root cause:** `authedRpc` default timeout 10s era insuficiente pra `get_dashboard_payload` em cold-start emul (TLS handshake + supabase-js init).

**Fix:** `src/services/fetchDashboard.js` — 1ª tentativa timeout 30s, retry imediato 15s caso TimeoutError. Total worst-case 45s mas Dashboard popular em vez de skeleton stuck.

## Bug #0029 (P1) — FIXED

**Sintoma:** Após tap em DoseModal > Pular, UI mostrava "pulada" + banner amarelo "1 dose ainda não foi salva", mas BD permanecia `status='pending'` por 2+ minutos. CDP inspect mostrou queue com `{action:'skip', retryCount:0}` — drain function nunca tentou RPC.

**Fix em markDose.js:**
- `scheduleRetryDrain()` chamado em catch AuthLost + Network (force timer 5s backoff)
- `setTimeout(drainPendingMutations, 5000)` belt-and-suspenders pós `queueAdd()`
- Watchdog interval 30s → 10s

Validado QA round 3 (2026-05-25 21:12 BRT): mark Pular → BD `skipped` em <10s, sem precisar restart.

## Realtime cross-account (Opção D `patientId.in`)

**Diff vs v0.2.8.2:** Cada user agora subscreve com filter `patientId.in.(uuid1,uuid2,...)` que combina:
- pacientes próprios (owner)
- pacientes recebidos via share (`patient_shares.sharedWithUserId=user`)
- pacientes compartilhados outbound (`patient_shares.ownerId=user`)

Hook `useAccessiblePatientIds` substitui `useHasActiveShares` (v0.2.8.2). useRealtime agora aplica gate triplo: `manager.isActive + hasCollabContext + patientIds.length > 0`. Egress zero pra user solo (sem shares).

QA empírico v0.2.8.3 round 3 (2026-05-25):
- Patient INSERT cross-account: aparece para sharegiver via Realtime (precisa restart se app estava em background)
- Dose INSERT cross-account: aparece em REAL TIME no S25U sem restart ✅
- Dose UPDATE cross-account: sync correto pós-restart, real-time intermitente (Samsung kill)
