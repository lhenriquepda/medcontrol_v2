# Release v0.2.8.4 — 2026-05-25 (vc 106)

> Bug crônico desde v0.2.6.6 "fila stuck mesmo com app aberto + internet OK" finalmente atacado na raiz com cache local Zustand persistido.
> Validado empiricamente em Samsung S25 Ultra real device.

## Escopo

Hotfix da regressão arquitetural v0.2.7.0 (TanStack persist removido sem substituto). Padrão WhatsApp/Gmail aplicado: cache local sobrevive Samsung kill agressivo, UI imediato pós-boot, fetchDashboard sincroniza em paralelo.

## QA empírico S25U — antes vs depois

| Cenário | v0.2.8.3 | v0.2.8.4 |
|---------|----------|----------|
| Force-kill + reabrir (UI populada) | 15–30s skeleton stuck | **387ms** cache hidratado |
| Marcar dose runtime → BD persistido | 2+ min stuck | **1583ms** queue→drained→`_confirmedAt` |
| Cascade cassete resume (3-5 RPCs fetchDashboard) | 5× egress | **1×** (coalesce window 2s) |
| User solo sem shares (subscribe Realtime) | 4 listeners ativos (regressão) | **0** subscribe (gate restaurado) |

## 7 mudanças

### M1 — Persist Zustand stores (raiz do fix)
**Arquivos:** `src/state/persistStorage.js` (novo) + `src/state/{dose,patient,treatment}Store.js` + `src/hooks/useAuth.jsx` (clear no signOut)

`patient/treatment/doseStore` migrados de Map em memória pra `zustand/middleware persist` com `Capacitor Preferences` como backing storage. Padrão WhatsApp/Gmail — cache local sobrevive Samsung One UI 7 kill agressivo.

Boot flow:
1. Zustand persist hydrate cache → UI imediato (skeleton-free, 387ms validado)
2. Paralelo: `fetchDashboard()` pega delta server
3. `setAllDoses(...)` sobrescreve → UI atualiza in-place sem flicker

`partialize` converte `Map.entries()` → Array (JSON-safe) + `merge` reconstrói Map. `_snapshots` NÃO persiste (runtime-only — optimistic rollback).

**Bug runtime detectado durante QA + corrigido:**
Adapter original usava `await import('@capacitor/preferences')` dinâmico — **hung indefinidamente** quando chamado pelo Zustand persist middleware (provavelmente circular dep com state/doseStore). CDP timeout 3s revelou o hang.
Fix: `Capacitor.Plugins.Preferences` direto (injetado pelo bridge native antes do React mount).

### M2 — Coalesce window fetchDashboard 2s
**Arquivo:** `src/services/fetchDashboard.js`

Cascade resume típico dispara 5× `fetchDashboard` em ~1.5s (useAppResume + onlineManager bridge + Realtime catchup + visibilitychange + accessible-patient-ids invalidate). Window 2s pós-resolve re-serve mesmo result → **1 RPC real**, não 5.

```js
const COALESCE_WINDOW_MS = 2_000
if (lastResult && (Date.now() - lastResolvedAt) < COALESCE_WINDOW_MS) {
  return lastResult
}
```

`forceRefetchDashboard()` (pull-to-refresh) burla window — sempre fetch fresco.

### M3 — Drain batch chunks 3
**Arquivo:** `src/services/markDose.js` `_runDrain`

Antes: `Promise.allSettled(groups)` paralelo all-at-once. Backlog 50 doses = 50 RPCs simultâneos → connection pool Supabase Pooler estoura.
Agora: chunks de 3 + early-exit em transient fail (scheduleRetryDrain retoma).

```js
const CHUNK_SIZE = 3
for (let i = 0; i < groups.length; i += CHUNK_SIZE) {
  const chunk = groups.slice(i, i + CHUNK_SIZE)
  await Promise.allSettled(chunk.map(g => _drainDoseGroup(g, ...)))
  if (anyTransientFailed) break
}
```

Backlog típico 1-5 doses: drena em 1-2 rodadas (~2-4s validado QA).

### M4 — Realtime debounce 1500→3000ms unified
**Arquivo:** `src/hooks/useRealtime.js`

`refetchTimer` único compartilhado entre N listeners (doses/treatments/patients/patient_shares × 2). Burst de evento cross-account (cuidador marca 5 doses simultâneo) → 1 fetchDashboard. Alinhado com M2 (coalesce 2s + debounce 3s = ~80% redução egress em cenários storm).

Trade-off: 3s delay percebido entre evento server e UI atualizar (vs 1.5s antes). Aceitável.

### M5 — refetchOnWindowFocus false global
**Arquivos:** `src/main.jsx` + `src/hooks/useDoses.js`

Antes: TODA query refetchava ao volta foco → storm cascade (visibilitychange + focus + appStateChange ~simultâneo). 10-15 queries refetch paralelo + fetchDashboard + drain + Realtime catchup = pico egress.
Agora: default `false`, hooks UI-imediato override:
- `useDoses` (DoseHistory/Reports/Analytics) → true
- `useAccessiblePatientIds` (detectar share novo) → true

Demais queries (templates, sos_rules, profile) ficam stale 30s. `useAppResume.refetchQueries({type:'active'})` cobre quando volta foco.

### M6 — Restaurar gate `hasCollabContext`
**Arquivo:** `src/hooks/useRealtime.js` linha 66

Regressão round 4 v0.2.8.3 — removeu gate `hasCollabContext` pra teste-free detectar primeiro share INSERT em real-time. Custo: TODO user solo subscrevia 4 listeners patient_shares×2 + sos_rules + treatment_templates → egress contínuo desnecessário (~80% base solo).

Gate restaurado:
```js
if (!hasSupabase || !user || !isActive || !hasCollabContext) return
```

Trade-off: primeiro share recém-criado não aparece em real-time pro user solo. `useAccessiblePatientIds.refetchOnReconnect/refetchOnWindowFocus` cobre detect via pull-to-refresh ou navegar Compartilhar. Aceitável (criar share é evento raro).

### M7 — Mutex zombie killer 60s
**Arquivo:** `src/services/markDose.js`

`currentDrainPromise` stuck zombie (fetch hang sem timeout, exception perdida) bloqueava todos drains subsequentes → queue NUNCA drenava de novo. Cenário BUG #0029 v0.2.8.3.

```js
const MUTEX_ZOMBIE_TIMEOUT_MS = 60_000
if (currentDrainPromise && (Date.now() - currentDrainStartedAt) > MUTEX_ZOMBIE_TIMEOUT_MS) {
  console.warn('[drain] zombie mutex detected (>60s), force-clearing')
  currentDrainPromise = null
}
```

Threshold 60s = cold-start budget (30s) + retry (15s) + margem 15s.
